# v0.32.0 → v1.0 差距评估

> 评估基准：**v0.32.0**（含本轮 16 个提交，`48ac894`）。
> 前一份：[`v1.0-gap.md`](v1.0-gap.md)（基准 v0.31.0）。**这一份是它的续版，不覆盖它** ——
> 那份的每条结论在它自己的基准上依然成立，这一份只写**本轮改变了什么**和**现在还剩什么**。
> 每一条都带来源：**本轮实测/变异红**，或 **"出自本文件/前一份的记录，未在本轮复核"**。
>
> **结论一句话：技术账上安全线闭环了；但把剩下的代码缺口全部做完，也不会让它变成 1.0 ——
> 因为 1.0 要的是"可证明它站得住"，而那一类工作这一轮一件都没做。**
>
> **自评折扣**：做这些活的和写这份评估的是同一批 AI。这与当初那份"98/100 自评"是**同一个形状**，
> 所以这份同样该打折。证据留在了 repo 里（变异红、门禁、CHANGELOG），但那不等于独立验证。

## 一、本轮跨过的（有变异红 / 实测支撑）

| 面 | 改变 | 证据 |
|---|---|---|
| **Raft 入站** | 从**零认证**（`ClusterAuth` 全仓库零调用点）到逐帧 HMAC + `error.ClusterAuthRequired` 门禁 | 3 条变异红（断言红） |
| **Raft 成员** | `handleVoteRequest` / `handleAppendEntries` / `handleInstallSnapshot` 都校验成员 | 2 条变异红 |
| **选举** | 修掉**两条独立缺陷**：peer id 空间不一致（票被丢弃）、票数 off-by-one（N=2 结构上不可能选出 leader） | 各 1 条变异红；后者用探针**实测**过 `leader` 断言 |
| **总线入站** | 从**根本没有帧**（一次 `readSome` = 一条消息：跨读丢包、一次读两条丢第二条）到定长帧 + L1 | 2 条变异红（含"跨两次写"） |
| **总线身份** | `identityKey` 换成**每节点凭证 + 挑战-应答双向握手**；`source_node` 第一次成为可验证的事实 | 核心判据 1 条变异红（`expected 0, found 2`） |
| **WS** | `ws_uring` 并轨到共享校验器（此前 `start()` 不编译 ⇒ `processData` **从未被分析**，缺陷是潜伏的）、UTF-8、>4KiB 单帧、握手校验 | 2 条变异红 |
| **执行层** | `ClusterServer` 并发（handler 加 context，删掉两个 `threadlocal`）；入站 `AppendEntries` 截断 + 解码侧上界 | 各 1 条变异红 |
| **`sockread`** | `setRecvTimeout`/`setSendTimeout` 会 **panic** 而非 warn（`EINVAL => unreachable`）；AF_UNIX 上对端关闭即触发 | TCP 与 AF_UNIX 双探针 + 1 条变异（abort） |

**这一轮最值钱的一条结论**：`identityKey = HMAC(cluster_secret, claim)` **不绑定身份、也不可能绑定** ——
持有共享 secret 的人能推导任何节点的 key。**在那之前，"集群内任何节点都能冒充任何节点"**，
所以前面几条认证的意义都有上限。现有方案换成了每节点凭证。

## 二、剩余差距：A（写代码能关的）

**逐条状态都写明"谁验证的"**。标 `[未复核]` 的是出自本仓库文档/先前轮次的记录，本轮没有重新确认。

1. **Raft 侧的 L1 同样不绑定身份** —— 共享 PSK 的 `ClusterAuth`。**与总线刚做的那件同形**，
   而总线那套握手现在是现成模板。**这是本轮结束后的头号技术缺口。**
2. **无加密** —— 全程帧明文。身份 ≠ 机密性，要 TLS/边车（`TlsTransport.zig` 文件头已写明 mTLS 目前需边车）。
3. **无密钥轮换 / 撤销** —— 静态成员表 + 静态 key。
4. **Raft 日志的无界总增长** —— `compactLog` 需要应用提供 snapshot 源，属**压缩策略决策**；
   本轮只修了"入站帧的条目数上界"（截断），**没有**修总增长。`[未复核]`
5. **非阻塞 IO** —— `ConnPool` / libpq 仍可能占住 pooled worker。`[未复核]`，先前记为 P0 候选。
6. **Scheduler / 执行层剩余** —— 公平性加权、batch 调优、affinity/NUMA、优先级；
   `StopPolicy` 与执行模式解耦；Supervision tree；Replay→WAL；deterministic runtime；
   Distributed Worker 统一；μs 级 timer。`[未复核]`，出自 v1.0-gap.md 与更早的矩阵。
7. **`ws_uring` 只在 Linux 生效** —— 本轮只能验"能编译 + 解析器并轨 + 共享校验器"，
   **真实 io_uring 行为在 macOS 上跑不了**。
8. **`ConcurrentError`（并发到限的拒绝分支）树内不可测** —— `testing.io` 的 `concurrent_limit`
   是 `unlimited`。这是"不可测"，不是"没测"。
9. **混合版本是硬切** —— Raft 的帧格式与总线的握手都变了，**两个方向都听不懂**。
   这是刻意的（不引入"降级到不认证"的路径），但它把下面 B-11 变成**必须做**的一件事。

## 三、剩余差距：B（要"证据"，不只是"代码"）—— **这才是 1.0 的真门槛**

10. **不是"没有 soak 目标"，是"没有覆盖本轮改动的那一个"。** 本轮实测了这点：

    ```
    zig build soak -Dsoak-clients=64 -Dsoak-iterations=200 -Dtest-force-run=true
    → Build Summary: 5/5 steps succeeded; 2/2 tests passed            （5 秒）
    ```

    它**通过**了，但两件事要如实说：

    | 事实 | 证据 |
    |---|---|
    | 只覆盖 **HTTP + 租户隔离**（跨租户泄漏、FrozenMap 并发读、fd/slot 不泄漏） | `src/soak.zig` 文件头自述 |
    | **完全不碰** cluster / bus / runtime | `grep -cE 'ClusterServer\|DistributedEventBus\|RaftElection\|Runtime' src/soak.zig` → **0** |
    | **5 秒**跑完 64×200 —— 是并发测试，不是"长跑" | 上面的 Build Summary |

    `zig build runtime-stress` 覆盖 **runtime**（worker/pool/就绪环/定时器/监督树），
    而它文件头**自己写明**了另一件关键的事：它之所以存在，是因为
    "`zig build soak` … never touches the runtime … **在每一个短的、单线程测试里都是对的，
    只有在长交织下才变成缺陷**"。它同样不碰 cluster / bus（`grep` → **0**）。

    **覆盖图**：

    ```text
    zig build soak           → HTTP + 租户隔离
    zig build runtime-stress → runtime（worker/pool/scheduler/timer/supervision）
    本轮改动的 cluster/bus    → **没有任何长时覆盖**
    ```

    而本轮最需要长跑的正是最后那一格：`ClusterServer` 的新生命周期协调（并发分发 +
    `dispatching`/`running` 的 `seq_cst` 握手 + `stop()` 的 await）、总线的握手与每连接绑定
    （新的协议步骤）、入站 `AppendEntries` 截断（新的 leader/follower 交互）。
    **这三处只有集成级用例，没有 soak。**

    > **这一条修正了我自己的建议。** 我上一轮说"如果只做一件，就做 soak + 混合版本对跑"，
    > 好像 soak 能证伪本轮的改动 —— **它不会，它跑的是另一个子系统。**
    > 要证伪本轮得**新建**一个 cluster 长时 harness：多节点 `ClusterBootstrap` 长跑、
    > 真实选举/心跳/复制 + 总线发布流量，**周期性**断言（消息不丢、leader 不抖、
    > RSS 不爬升、fd 不泄漏），而不是重跑现成的 soak。
11. **混合版本从未实测对跑。** 本轮反复记录"硬切"，但**一次都没真跑过**新旧两个二进制。
12. **没有 fuzz。** 而帧解析、握手、JSON 解析恰好是最该 fuzz 的三个面。
13. **benchmark 证据仍薄。** `check-bench` 的 `TimerWheel x100K` 是**双峰**指标 ——
    本轮**实测**：同一棵未改动的树上 3 次里红 1 次（`9.33 OK / 8.36 OK / 13.63 FAIL`）。
14. **没有独立验证。** 所有"已闭环"都出自同一批 AI + 自证，**包括我自己的变异复核**。
15. **有一条端到端结论是静态推导**：CL/TE 请求走私那条**没有起真实前置代理**（先前已如实标注）。

## 五、判断

```text
按"功能 + 安全完成度"      ≈ 1.0 的 85%
   剩下的 15% 里
   ├── A 代码能关的（8–10 条，多数有界）  → 一条条做，可做完
   ├── B 证据（soak/混合版本/fuzz/独立验证） → 这才是门槛
```

**把 A 全部做完也不会让它变成 1.0。** 1.0 意味着"**可证明**它在生产里站得住"，
而那需要的东西 —— 长跑、混合版本对跑、独立的人来验 —— **这一轮一件都没做**。

### 如果只能做一件

**soak + 混合版本对跑。**

理由是它们会**证伪**本轮这批改动。本轮所有改动都是 AI 写的、由我自证的，
最需要的恰恰是"**有没有东西能推翻它**"。风险最高的是这几处（都是"改对了但没长跑过"）：

- `ClusterServer` 并发 + `stop()` 的 `dispatching` 握手（新的生命周期协调）；

## 七、附录：ubuntu 为什么红了 —— 两层，都不是产品代码

从 `3a7decb` 起，ubuntu 的 `Build & Test` 就是红的；红的样子是
**`Run tests` 挂满 25 分钟**后被 action 超时打断。把它拆开：

### 第 1 层：`| tee` 把"失败"变成了"挂死"（测试台的问题）

`zig build test 2>&1 | tee log` 里的那个管道是元凶。Zig 的构建器失败后会留下一个
仍然握着 stdout 的子进程（CI 收尾日志里就写着 `Terminate orphan process: pid (2921) (test)`），
`tee` 等不到 EOF 就一直等，shell 也就一直等 `tee` —— **报错发生在 07:20:12，日志里
早就打印了 `failed command`，而这一步直到 07:45 才因超时结束。**

机制可复现（与 Zig 无关的最小形态）：

```bash
time bash -c 'bash -c "sleep 4 & echo done"' 2>&1 | tee /tmp/a.log   # real 4.017s
time bash -c 'bash -c "sleep 4 & echo done"' > /tmp/b.log 2>&1       # real 0.009s
```

修法：`scripts/ci-run-logged.sh` —— 输出由 shell 重定向写文件、结束后 cat、退出码是
命令自己的。五处 `| tee` 全部改走它。

### 第 2 层：真正的失败是一个**竞争断言 + 缺 `stop()`**（测试的问题）

在 Linux 容器里把同一棵树跑起来（`zmodu audit` 无关，用 `scripts/test-fast.sh --force-run --db all --filter .`）
复现了挂死，然后对挂住的进程 dump 线程栈：

```text
Thread 1 (main)   __pthread_clockjoin_ex ← Thread.join        Server.zig:4292   ← 测试在 join
Thread 2 (server) accept4                                      Server.zig:2437   ← 服务器还在 accept
```

`4292` 就是那个 `defer th.join()`。也就是说测试**断言先失败了**，失败路径让
`server.stop()` 没被执行，于是被 defer 的 `join()` 永远等一个没人停的服务器。

断言原文（日志第 517 行）：

```text
517/1461 api.Server.test.WebSocket upgrade: ... a Connection token list gets 101...expected 1, found 0
```

`expectEqual(1, ws_upgrade_state.connects)` —— 101 已经到了客户端，但服务端线程还没执行
`on_connect`。**这是测试里的竞争**：响应先写 101、后调 `on_connect`，而客户端读完状态行
立刻读那个计数器。macOS 上调度恰好让服务端先跑完，Linux 上就翻车；而且那个计数器
当时还是**非原子**的（读写跨线程）。

修法（`src/api/Server.zig`）：计数器改 `std.atomic.Value(usize)`；加一个有界等待
`expectConnects(1)`（2s）；三个用 `Thread.spawn(server.start)` 的 WS 测试都补上
`defer server.stop();`（声明在 `defer th.join();` **之后**，LIFO 保证先停后 join）。
**"断言失败 → 挂死"这个形状本身就是缺陷**，比那一次竞争更值得修。

### 第 3 层：修完上面两个，全量**还是**挂 —— 这次是产品代码

修完再跑 Linux 全量，挂在另一个地方，同一份 gdb 手法：

```text
Thread 1 (main)       Io.Group.await  ← DistributedEventBus.stop()   :350
Thread 3 (async task) accept4         ← acceptLoop                   :392
测试名：core.DistributedEventBus.test.two credentialed nodes bind
        over the network and exchange an event
```

**`close()` 唤不醒已经阻塞在 `accept()` 的线程**（Linux 语义），所以 `acceptLoop`
永远读不到 `is_running` 的变化，`stop()` 里的 `fiber_group.await` 就永远等。
`Server.closeListener` 早就知道这条并写了 `shutdown()` 绕法，但另外四个自己
accept 的地方都是裸 `deinit`：`DistributedEventBus`、`ClusterServer`、
`WebSocketServer`、`WebMonitor`。收成一个 `sockread.closeListener(io, *Server)`，
五处都走它。

**验证**（同一棵树，Linux 容器）：

```text
修复前：挂死，直到 timeout
修复后：run test 1440 pass, 21 skip (1461 total)   EXIT=0
macOS：1555/1576，21 skipped，0 failed（与改动前一致）
```

这一个是**真正的产品缺陷**，不是测试问题：在 Linux 上 `stop()` 不返回意味着进程
无法干净退出。

### 顺带澄清：日志里那两行 `-isystem` 报错不是失败

```text
error: warning: add "/usr/include/postgresql" to header searchlist '-isystem' conflicts with '-I'
```

它在 `zig build` 里也出现，而那次构建是 **`Build Summary: 8/8 steps succeeded`、退出码 0**。
成因已定位：`pkg-config --cflags libpq` 给 `-I/usr/include/postgresql`，而
`examples/_shared/db_link.zig` 自己又 `addSystemIncludePath` 了同一个目录，两种拼法冲突 →
Zig **重试一次**并成功。容器里装了 pkg-config 就能复现、不装就不出现 —— 即：
**这是日志噪音，不是本地失败的原因**，但它把诊断带偏了整整一轮。

同一类噪音还有一条 `failed command: .../test --cache-dir=... --listen=-` —— 被点名
的那个二进制单独跑是 `All 1 tests passed`、退出码 0，而 `zig build test` 整体也
`EXIT=0`。两条都是这套 dev 工具链在"先失败一次、再重试成功"时打出来的。

## 八、附录：ubuntu 转绿之后，macOS 连着红了两次

同一个 job（`Build & Test (macos-latest)`）、同一个测试二进制（`runtime-stress` 的
smoke 配置），两次失败**不是同一个原因** —— 这正是"红了先复跑"的价值：

| 次数 | 结果 | 读数 |
|---|---|---|
| 第 1 次 | `1 failed` | `[stress] FAIL: only 2 of 5 window(s) covered all four paths` |
| 第 2 次（复跑） | `1 crashed` | `thread 15004 panic: reached unreachable code` @ `src/runtime/scheduler.zig:634` in `push` |

### 8.1 window_coverage：把机器速度当成了运行时属性（已改）

判据要求"5 个采样窗里至少 3 个窗四条路径都推进过"（timer fire / receive /
cpu dispatch / blocking dispatch），因为零分配探针只有走全四条路径才有意义。
但**一个固定 2s 预算里能拿到几个这样的窗，取决于机器**：那台 2 核 runner 只
采到 6 个样本、覆盖 2 个（同一次运行的 `push_failures=0 high_water=2 capacity=4`
说明 ring 根本没满，运行时是健康的）。

改法：地板变成 `-Druntime-stress-min-windows`（默认 3）。smoke 配置固定为 **1**，
长跑 `zig build runtime-stress` 保持 3 —— smoke 的职责是"这条路径至少被走过一次、
每个检查都被求值"，长跑才是量地板的地方。本机实测：smoke 仍 PASS，长跑仍 PASS。

### 8.2 `push` 断言：**未定论**，只加了耐心，没有假装修好（⚠️）

栈（原文，来自 CI 日志）：

```text
thread 15004 panic: reached unreachable code
  std/debug.zig:442 assert
  runtime/scheduler.zig:634 in push            std.debug.assert(false);
  runtime/scheduler.zig:695 in runOne          if (item.pending(...) != 0 and !item.queued.swap(true, .acq_rel)) self.push(item);
  runtime/scheduler.zig:674 in turn
  runtime/scheduler.zig:708 in poolMain
```

即：`runOne` 交还令牌时，`push` 在 1M 次 `spinLoopHint` 之后仍被告知"环满"。
按文件头那条容量不变式（D4：一个 worker 最多一个令牌 ⟹ 占用 ≤ worker 数 ⟹ 每个
push 必有槽），**环满=bug**。但我**没有证明**它是 bug，也没有证明它不是：

- 支持"假满"的：同一次任务里完成过的那一轮 `high_water=2/capacity=4`、
  `push_failures=0`；消费端在 `tryPop` 里"已推进 `dequeue_pos`、尚未释放槽位"的
  窗口是真的，而**自旋帮不到一个被 OS 换下 CPU 的消费者**。
- 支持"真满"的：容量按 `max_pooled_workers + pool_threads` 推出来，已经把这个
  窗口算进去了；真满只能来自 D4 被破坏。

所以我只做了不改变语义的那一半：**自旋预算之后先 `Thread.yield()`（4096 轮）再
断言**。断言还在（真满仍是 panic + `ready_push_failures`），只是不再把"消费者被
换下 CPU"判成环满。

**复现尝试（失败，如实记）**：Linux 容器 `--cpus=1`（模拟那台 2 核 runner 的 CPU
饥饿）+ smoke 配置，**连跑 40 次全绿**；macOS 本机全量 3 次也全绿。所以这条
**没有被证明修好**，只被证明"不再用自旋去等一个不在 CPU 上的线程"。它在 macOS CI
上的出现率大约是 1/2 与 1/4（两次尝试各命中一次不同症状），要定论得在多核共享
runner 上批量跑，或用 `perf`/`dtrace` 抓那个窗口。

### 8.3 第三次 macOS 红：监控树测试的 check-then-assert（已修，证据吻合）

第三次复跑的失败与上面两个都不同：

```text
error: 'runtime.runtime.test.Supervision (§14.5): a nested group escalates to its
       parent, and the parent's policy decides' failed:
  expected 2, found 1
  runtime.zig:5947   try std.testing.expectEqual(@as(u32, 2), inner_inits.load(.monotonic));
```

这个测试**自己**就写着这条规律，只是只改了一半 —— 下面那段注释原文：

> 等的是这个测试**要断言的那个计数器**，不是 `group_restarts`：重建会先动
> 后者、再跑 `init`（`rebuildWorker`），所以"等 `group_restarts` 然后读 init
> 计数器"是 check-then-assert 竞态。它在一次全量里闪过一次。

`outer_inits` 按这条规矩改了，**紧挨着它上面的 `inner_inits` 没改** —— 于是

本机过滤跑该测试：1 selected, 1 passed；全量 1555/1576。
