# v0.32.0 → v1.0 差距评估

> 评估基准：**v0.32.0**（含本轮 16 个提交，`48ac894`）。
> 前一份：[`v1.0-gap.md`](v1.0-gap.md)（基准 v0.31.0）。**这一份是它的续版，不覆盖它** ——
> 那份的每条结论在它自己的基准上依然成立，这一份只写**本轮改变了什么**和**现在还剩什么**。
> 每一条都带来源：**本轮实测/变异红**，或 **"出自本文件/前一份的记录，未在本轮复核"**。
>
> **结论一句话：技术账上安全线闭环了；但把剩下的代码缺口全部做完，也不会让它变成 1.0 ——
> 因为 1.0 要的是"可证明它站得住"，而那一类工作这一轮一件都没做。**
>
> **自评折扣**：做这些活的和写这份评估的是同一批 AI。这与当初那份"98/100 自评"是**同一个形状**，
> 所以这份同样该打折。证据留在了 repo 里（变异红、门禁、CHANGELOG），但那不等于独立验证。

## 一、本轮跨过的（有变异红 / 实测支撑）

| 面 | 改变 | 证据 |
|---|---|---|
| **Raft 入站** | 从**零认证**（`ClusterAuth` 全仓库零调用点）到逐帧 HMAC + `error.ClusterAuthRequired` 门禁 | 3 条变异红（断言红） |
| **Raft 成员** | `handleVoteRequest` / `handleAppendEntries` / `handleInstallSnapshot` 都校验成员 | 2 条变异红 |
| **选举** | 修掉**两条独立缺陷**：peer id 空间不一致（票被丢弃）、票数 off-by-one（N=2 结构上不可能选出 leader） | 各 1 条变异红；后者用探针**实测**过 `leader` 断言 |
| **总线入站** | 从**根本没有帧**（一次 `readSome` = 一条消息：跨读丢包、一次读两条丢第二条）到定长帧 + L1 | 2 条变异红（含"跨两次写"） |
| **总线身份** | `identityKey` 换成**每节点凭证 + 挑战-应答双向握手**；`source_node` 第一次成为可验证的事实 | 核心判据 1 条变异红（`expected 0, found 2`） |
| **WS** | `ws_uring` 并轨到共享校验器（此前 `start()` 不编译 ⇒ `processData` **从未被分析**，缺陷是潜伏的）、UTF-8、>4KiB 单帧、握手校验 | 2 条变异红 |
| **执行层** | `ClusterServer` 并发（handler 加 context，删掉两个 `threadlocal`）；入站 `AppendEntries` 截断 + 解码侧上界 | 各 1 条变异红 |
| **`sockread`** | `setRecvTimeout`/`setSendTimeout` 会 **panic** 而非 warn（`EINVAL => unreachable`）；AF_UNIX 上对端关闭即触发 | TCP 与 AF_UNIX 双探针 + 1 条变异（abort） |

**这一轮最值钱的一条结论**：`identityKey = HMAC(cluster_secret, claim)` **不绑定身份、也不可能绑定** ——
持有共享 secret 的人能推导任何节点的 key。**在那之前，"集群内任何节点都能冒充任何节点"**，
所以前面几条认证的意义都有上限。现有方案换成了每节点凭证。

## 二、剩余差距：A（写代码能关的）

**逐条状态都写明"谁验证的"**。标 `[未复核]` 的是出自本仓库文档/先前轮次的记录，本轮没有重新确认。

1. **Raft 侧的 L1 同样不绑定身份** —— 共享 PSK 的 `ClusterAuth`。**与总线刚做的那件同形**，
   而总线那套握手现在是现成模板。**这是本轮结束后的头号技术缺口。**
2. **无加密** —— 全程帧明文。身份 ≠ 机密性，要 TLS/边车（`TlsTransport.zig` 文件头已写明 mTLS 目前需边车）。
3. **无密钥轮换 / 撤销** —— 静态成员表 + 静态 key。
4. **Raft 日志的无界总增长** —— `compactLog` 需要应用提供 snapshot 源，属**压缩策略决策**；
   本轮只修了"入站帧的条目数上界"（截断），**没有**修总增长。`[未复核]`
5. **非阻塞 IO** —— `ConnPool` / libpq 仍可能占住 pooled worker。`[未复核]`，先前记为 P0 候选。
6. **Scheduler / 执行层剩余** —— 公平性加权、batch 调优、affinity/NUMA、优先级；
   `StopPolicy` 与执行模式解耦；Supervision tree；Replay→WAL；deterministic runtime；
   Distributed Worker 统一；μs 级 timer。`[未复核]`，出自 v1.0-gap.md 与更早的矩阵。
7. **`ws_uring` 只在 Linux 生效** —— 本轮只能验"能编译 + 解析器并轨 + 共享校验器"，
   **真实 io_uring 行为在 macOS 上跑不了**。
8. **`ConcurrentError`（并发到限的拒绝分支）树内不可测** —— `testing.io` 的 `concurrent_limit`
   是 `unlimited`。这是"不可测"，不是"没测"。
9. **混合版本是硬切** —— Raft 的帧格式与总线的握手都变了，**两个方向都听不懂**。
   这是刻意的（不引入"降级到不认证"的路径），但它把下面 B-11 变成**必须做**的一件事。

## 三、剩余差距：B（要"证据"，不只是"代码"）—— **这才是 1.0 的真门槛**

10. **不是"没有 soak 目标"，是"没有覆盖本轮改动的那一个"。** 本轮实测了这点：

    ```
    zig build soak -Dsoak-clients=64 -Dsoak-iterations=200 -Dtest-force-run=true
    → Build Summary: 5/5 steps succeeded; 2/2 tests passed            （5 秒）
    ```

    它**通过**了，但两件事要如实说：

    | 事实 | 证据 |
    |---|---|
    | 只覆盖 **HTTP + 租户隔离**（跨租户泄漏、FrozenMap 并发读、fd/slot 不泄漏） | `src/soak.zig` 文件头自述 |
    | **完全不碰** cluster / bus / runtime | `grep -cE 'ClusterServer\|DistributedEventBus\|RaftElection\|Runtime' src/soak.zig` → **0** |
    | **5 秒**跑完 64×200 —— 是并发测试，不是"长跑" | 上面的 Build Summary |

    `zig build runtime-stress` 覆盖 **runtime**（worker/pool/就绪环/定时器/监督树），
    而它文件头**自己写明**了另一件关键的事：它之所以存在，是因为
    "`zig build soak` … never touches the runtime … **在每一个短的、单线程测试里都是对的，
    只有在长交织下才变成缺陷**"。它同样不碰 cluster / bus（`grep` → **0**）。

    **覆盖图**：

    ```text
    zig build soak           → HTTP + 租户隔离
    zig build runtime-stress → runtime（worker/pool/scheduler/timer/supervision）
    本轮改动的 cluster/bus    → **没有任何长时覆盖**
    ```

    而本轮最需要长跑的正是最后那一格：`ClusterServer` 的新生命周期协调（并发分发 +
    `dispatching`/`running` 的 `seq_cst` 握手 + `stop()` 的 await）、总线的握手与每连接绑定
    （新的协议步骤）、入站 `AppendEntries` 截断（新的 leader/follower 交互）。
    **这三处只有集成级用例，没有 soak。**

    > **这一条修正了我自己的建议。** 我上一轮说"如果只做一件，就做 soak + 混合版本对跑"，
    > 好像 soak 能证伪本轮的改动 —— **它不会，它跑的是另一个子系统。**
    > 要证伪本轮得**新建**一个 cluster 长时 harness：多节点 `ClusterBootstrap` 长跑、
    > 真实选举/心跳/复制 + 总线发布流量，**周期性**断言（消息不丢、leader 不抖、
    > RSS 不爬升、fd 不泄漏），而不是重跑现成的 soak。
11. **混合版本从未实测对跑。** 本轮反复记录"硬切"，但**一次都没真跑过**新旧两个二进制。
12. **没有 fuzz。** 而帧解析、握手、JSON 解析恰好是最该 fuzz 的三个面。
13. **benchmark 证据仍薄。** `check-bench` 的 `TimerWheel x100K` 是**双峰**指标 ——
    本轮**实测**：同一棵未改动的树上 3 次里红 1 次（`9.33 OK / 8.36 OK / 13.63 FAIL`）。
14. **没有独立验证。** 所有"已闭环"都出自同一批 AI + 自证，**包括我自己的变异复核**。
15. **有一条端到端结论是静态推导**：CL/TE 请求走私那条**没有起真实前置代理**（先前已如实标注）。

## 五、判断

```text
按"功能 + 安全完成度"      ≈ 1.0 的 85%
   剩下的 15% 里
   ├── A 代码能关的（8–10 条，多数有界）  → 一条条做，可做完
   ├── B 证据（soak/混合版本/fuzz/独立验证） → 这才是门槛
   └── C 治理                          → 不是技术问题，提交解决不了
```

**把 A 全部做完也不会让它变成 1.0。** 1.0 意味着"**可证明**它在生产里站得住"，
而那需要的东西 —— 长跑、混合版本对跑、独立的人来验 —— **这一轮一件都没做**。

### 如果只能做一件

**soak + 混合版本对跑。**

理由是它们会**证伪**本轮这批改动。本轮所有改动都是 AI 写的、由我自证的，
最需要的恰恰是"**有没有东西能推翻它**"。风险最高的是这几处（都是"改对了但没长跑过"）：

- `ClusterServer` 并发 + `stop()` 的 `dispatching` 握手（新的生命周期协调）；
- 总线的握手 + 每连接绑定（新的协议步骤，只有集成级用例，没有长跑）；
- 入站 `AppendEntries` 截断（新的 leader/follower 交互，只有单点用例）；
- 服务化路径下的 `sockread` 超时（AF_UNIX 修复只覆盖了已知形状）。

### 各条"未验证"的现状（照抄本仓库记录，不粉饰）

- 混合版本：**从未对跑**
- `ws_uring` 真实行为：**Linux 才能验**，本轮没验
- `ConcurrentError` 分支：**树内不可测**
- CL/TE 走私：**静态推导**，无真实代理
- 双实例 `permissionGateWith`（先前轮次）：**构造性论证**，无对拍
- `putAssumeCapacity → put`（先前轮次）：**代码级论证**，无行为红
- `BufferPool` 尺寸契约：**无行为红**（修复前后池状态相同），用例是钉子
