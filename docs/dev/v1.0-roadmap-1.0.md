## 一、1.0 的定义（先定这个，否则后面全是空话）

`v1.0-readiness-v0.35.md` 的 ~70% 与 `EVALUATION_2026-10.md` 的 82.6 分**不冲突**——
前者按 A/B/C 组判"能不能叫 1.0"，后者是加权评分判"值不值得用"。本文采用如下定义：

> **1.0-alpha = 功能与门禁完备 + 破坏性边界稳定 + 独立验证有计划、可复现、且已有一次外部交互**
> **不宣称**：生产可靠性已被第三方验证。

这个定义是**故意留了一格**。理由：

- **B-14（独立验证）不是靠写代码能关的。** 1008 个提交里`Antigravity Agent` 758、
  仓库所有者 `chy3xyz` 1，所有"已闭环"都出自同一批 AI 维护者，`README.md:224` 自己写着
  "no independent audit"。强行宣布 1.0 而不解决这一条，是**把项目的核心诚实资产花掉换了个版本号**。
- 但**它可以变成"有计划"**：材料齐备（`dev/reproducing-evidence.md` + 全部 artifact 可下载）
  且已有第一次外部接触（下游消费方 zweq，见 §三 阶段 3 · T3.2）。这是从 0 到 1 的质变。

**反过来说**：如果一定要等到真审计才敢叫 1.0，那这个项目可能半年都发不出版本。
0.x 的价值恰恰是"允许快速破坏"，而它现在每天发1–2 次——**先用完0.x 的红利，比急着贴 1.0 标签更有价值**。

## 三、阶段划分

###阶段 0：减速与定位（**本周，最高优先级**）

**为什么第一件事是这个**：目前 08 月 33 版、09 月 48 版、10 月 10 天 10 版。
99 个发布**全在 0.x**，近月 1–2 次/天。这个节奏本身在**否决 1.0**——
没有任何团队会把"一天发两次的 0.x"当生产依赖，而这是 1.0 要解决的第一件事。

1. **发布节奏降到每周一版**（或双周）。日常改动攒批次，不单独发patch。
   理由不是"发多了显得不专业"，而是**碎片化版本让用户无法升级**——
   现在从 v0.32 升到 v0.39 要跨 60+ 个版本，等于把破坏性变更摊平成"随时会坏"。
2. **停止在 0.x 里加功能**。冻结功能面，只做：修缺陷、补证据、改文档。
   理由：`A-6 加权`/`A-9` 两项之外的每一行新代码，都是**推迟 1.0 并增加审计面积**。
3. **破坏性变更清零**。已破 6/99 是不错的记录，1.0 前把这条守住。
   1.0 后语义化版本才有意义——这也是"1.0-alpha"和"1.0"的差别。

**产出**：`PRODUCTION_ROADMAP` 加一条"发布节奏"节；AGENTS.md 写明节奏约定。

### 阶段 1：补掉两项可写的 A 组（1–2 批次）

| 任务 | 内容 | 验收 |
|---|---|---|
| **T2.1 A-9 混合版本第三形状** | `ci-mixed-version.sh:42` 的 `case` 加一个形状。建议**"新侧先滚、再旧侧滚"** 的双向滚动（现在只有 old→new） |夜间 CI 出绿 + artifact |
| **T2.2 A-6 公平性加权** | `RUNTIME.md:710` 的克制是对的：**先加测量，再加旋钮**。第一步只加"按类别统计等待时长/饥饿次数"的 gauge，不改调度行为 | 新 gauge + 有baseline 后再谈加权 |

> **T2.2 的做法值得强调**：这个项目已有的好习惯是"**声明即契约、编译即反馈**"。
> 加公平性旋钮却不先测等待分布，等于把"没有测量就不加旋钮"的正确克制推翻。
> **建议：1.0-alpha 不实现加权，只实现测量。** 这样 A-6 的剩余面被正式缩小到"一个gauge + 一个决策"。

### 阶段 2：对外开源的真实准备（**这是 B-14 的前置**）

`stars 3 / forks 0 / 外部贡献者 0` 不是虚荣指标，它衡量的是**"出问题时能不能指望别人"**。
而一旦对外开源，B-14 才有解——**因为外部贡献者就是独立验证的载体**。

1. **README 顶部加"状态声明"**。现有"It is not / 采用前先定价"节质量很高，
   但要再加一句显式的成熟度声明：
   >本项目处于 **1.0-alpha 前期**：功能面已冻结，门禁完备，**尚无独立审计**。
   > 生产部署请自行评估 §「它不是什么」列出的边界。
   理由：**对外开源时最怕的不是项目不成熟，是成熟度被误读。** 主动说清楚比被人发现好。
2. **把 `dev/v1.0-readiness-v0.35.md` 更新到今天**。它现在是v0.35 快照且B-11 结论已过时。
   对外开源后这是**第一份被陌生人读的文档**，过时会直接损伤可信度。
3. **顺手修两处口径不一致**（实测发现，本文只标不改）：
   - `AGENTS.md:454` 写「phases 1–9 ✅」，`PRODUCTION_ROADMAP.md:133` 标题是「阶段 9 —（**演进中**）」。
   - `EVALUATION_REPORT.md` 仍标 v5 / 990-1009 测试（2026-08-27），已被 `EVALUATION_2026-10.md` 取代，
     但文件里仍写「综合 ~98/100」——**这个分数对外会被当真，需要在头部加失效标注**。
4. **`docs/EVALUATION_REPORT.md` 保留原地**（源码注释按路径引用它），但头部必须加失效声明。
5. **建issue 模板与"可证伪的 bug"模板**。这个项目的一切都是"读数 + 复现命令"，
   外部贡献者也应该按这个格式提issue。**这是把内部文化转成外部协作契约的最快方式。**

### 阶段 3：独立验证（**唯一没有终点的一条**）

B-14 没有技术解，只有组织解。三个可执行动作，按成本排序：

> **起点已经不是零**：框架**已被两个真实下游项目承载**
> （zenaipa全栈平台 · zasdoor IAM 系统，79 个后端测试），加上 zweq 的消费方评审互动
> 与 `neox33` 的 220 个提交。**要补的不是"有人用它"，而是"有人能推翻它"。**
> 这一步的性质因此更清楚了——dogfooding 压得出bug，但压不出**审计意见**。

#### T3.1 把复现材料做到"陌生人能跑"（本周，成本最低）

现有 `dev/reproducing-evidence.md` + artifact 已是不错的底子。对外开源前补：

- 一条**不依赖仓库环境**的复现路径（Docker 或干净 checkout + `bash scripts/ci-smoke.sh`）。
- 所有门禁的**期望输出贴进文档**（现在多半是描述性的）。
- 明确写"哪些结论**只有作者跑过**"。

理由：现在的"可复现"是**作者视角的可复现**。要变成证据，必须是**别人视角**的。

#### T3.2 邀请外部评审（成本中等，收益最高）

**已有的接触面（比"从零找人"强得多，但都不是审计）**：

| 接触面 | 关系 | 已有的真实交互 |
|---|---|---|
| 下游消费方 zweq | 外部使用方 | v0.39.8「消费方评审」批次（提的问题逐条属实后修复）、v0.39.6 下游泄漏豁免 |
| [**zenaipa**](https://github.com/chy3xyz/zenaipa) | 同所有者下游项目 | 依赖用 **git tag + content hash 双锁**（供应链姿势正确） |
| [**zasdoor**](https://github.com/chy3xyz/zasdoor) | 同所有者下游项目 | IAM/身份系统，**79 个后端测试**，直接吃框架 security 面（JWT/多租户/OIDC/会话吊销） |
| zmodu 仓库外部贡献者 | `neox33` | 220 提交 |

> **诚实标注**：后两个与 zigmodu **同一所有者 `chy3xyz`**，提交身份是 `shimonenator`
> （与仓库内的 `Antigravity Agent` 不同）。它们证明"**框架能承载真实项目**"——
> 尤其 zasdoor 的身份系统对安全面是硬压测——**但不能替代独立审计**，
> 因为作者自己决定实现方案、也自己判断实现对否。
> **B-14 判定维持未关。**

具体请求要**窄**——不要"帮我审一下整个项目"（会被礼貌拒绝），要具体到可回答的问题：

> 请用 v0.39.10 在你自己的项目里跑一个真实服务，重点回答：
> 1. `zigmodu doctor` 报出的问题哪些是真问题？
> 2. 18 个 `examples` 里你想抄的那个能不能跑通？
> 3. API 摩擦点Top 5 是什么？

窄请求的成功率远高于宽请求。

#### T3.3 接受"部分领域"的独立验证（现实路径）

**不必等完整审计。** 优先选**能被外部证伪且后果最严重**的领域，让外部先看这三个：

| 领域 | 为什么优先 | 期望形式 |
|---|---|---|
| **集群认证** | A-1/A-2/A-3 全在这里，且是"**误判为安全**"风险最高的领域 | 外部读 `ClusterAuth.zig` +跑 `cluster-sidecar` |
| **租户隔离** | `sql_tenant_column` 是编译期强制，**证伪成本低**（写一个越权查询，看是否编译失败） | 外部写一个尝试越权的测试 |
| **分配契约** | `alloc_contract_test.zig` 断言精确 0，**证伪只需加一条分配** | 外部加一行分配看是否变红 |

这三处的共同点：**外部能用极小的投入推翻一个具体断言**。
这正是"独立验证"需要的形态——不是让人通读17 万行，而是**让人推翻一条我们说对了的结论**。

> issue 模板是**外部信任从档 1 升到档 2 的唯一凭据**（§3.2）——

**这意味着 1.0-alpha 叫得成，但 90 分叫不到**——
差的那几分在"第三方审计"（外部信任档 3），**不是工程量能换的**。

**明确不做**（写下来是为了以后不再纠结）：

- 不实现分布式 Worker（A-6 移出范围）
